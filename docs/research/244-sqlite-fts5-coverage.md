# Research: SQLite (FTS5/sqlite-vec) coverage of mcp-memory's current schema

- Ticket: [argus#244](https://github.com/deanjstone/argus/issues/244)
- Map: [argus#242](https://github.com/deanjstone/argus/issues/242) (mcp-memory + watchtower: Supabase Postgres → SQLite)
- Scope: `~/repos/mcp-memory`, read-only. Sources: `supabase/migrations/001_memories.sql` through `006_add_memory_type.sql`, and `src/services/supabase.ts`, `src/services/embedding.ts`, `src/tools/memory.ts`, `src/types.ts` (the code paths behind the `memory_remember` / `memory_recall` / `memory_search` MCP tools).

## Summary

mcp-memory's entire schema is one table, `memories`, defined across six migrations. Every Postgres-specific construct in it has a workable SQLite equivalent — none of this blocks the cutover — but three things need deliberate design decisions rather than a mechanical translation:

1. **FTS is a generated `tsvector` column + GIN index**, queried via Supabase's `.textSearch(..., { type: "websearch" })` helper (`websearch_to_tsquery`). SQLite has no generated-column-into-virtual-table mechanism, so the FTS5 equivalent needs an external-content `fts5` virtual table kept in sync via `INSERT`/`UPDATE`/`DELETE` triggers on `memories`, and `websearch_to_tsquery`'s syntax (`-word` exclusion, implicit AND, quoted phrases) needs a small query-string translator since FTS5's own MATCH syntax differs (`NOT` instead of `-`, no direct websearch mode).
2. **The pgvector column is not dead code** — it's actively populated and queried today whenever `OLLAMA_HOST` is configured (confirmed set in this deployment's `.env`), which is the common case for local stdio use. `searchMemories()` tries the `search_memories_semantic` RPC (cosine similarity via `ivfflat`) first and only falls back to FTS if that RPC errors or returns zero rows. A SQLite port needs a real `sqlite-vec` (`vec0`) virtual table and a KNN query, not just an FTS5-only design — semantic search is the primary path, not an optional upgrade.
3. **The Postgres RPC (`search_memories_semantic`) and the "smart" `updated_at` trigger** both need porting: the RPC becomes a plain parameterized SQL query against the `vec0` table (SQLite/sqlite-vec has no stored-procedure/RPC concept), and the trigger becomes a SQLite `AFTER UPDATE ... WHEN NEW.updated_at IS OLD.updated_at` trigger issuing a follow-up `UPDATE` (SQLite's `recursive_triggers` pragma is off by default, so this doesn't infinite-loop the way a naive port might fear).

Everything else (RLS, the `text[]` tags column, the `memory_type` enum, `gen_random_uuid()`) has a standard, low-risk SQLite substitute — mostly "push the constraint into the application layer," which mcp-memory already does today via Zod schemas in `src/tools/memory.ts`.

## Things with no clean 1:1 equivalent (prose)

- **Row-level security (item 11)** is the one construct with no SQLite analog at all, not even an awkward one — SQLite has no concept of connection roles. This is fine because the RLS policy was purely a Supabase-connection-model safeguard (service-role key bypasses it; no other role was ever meant to reach the table), and mcp-memory's SQLite deployment will have exactly one trusted writer (the MCP server process) rather than multiple Postgres roles sharing a database. The security boundary just moves from "database enforces it" to "only the MCP server process holds the SQLite file handle" — worth a one-line callout in whatever ADR formalizes the cutover, not a design problem to solve.
- **`websearch_to_tsquery` → FTS5 MATCH syntax (item 15)** is the one place where "equivalent" isn't quite true out of the box — it's a small adapter function, not a drop-in swap. The current `memory_search` tool description promises `AND, OR, quotes, minus` (`src/tools/memory.ts:159`); FTS5 natively gives AND/OR/quotes but requires rewriting bare `-word` tokens to `NOT word` before constructing the MATCH string. Recommend writing this translator with unit tests before cutover, since it's user-facing query syntax that agents (Claude Code sessions) actively rely on via `memory_search`.
- **Stored function → app-level query (item 14)**: not a coverage gap so much as a shift in where the logic lives — the RPC's `STABLE`/`LANGUAGE sql` wrapper was purely organizational in Postgres. Moving the equivalent query inline into the SQLite service layer (alongside the FTS query) is strictly simpler, since sqlite-vec has no server-side function registration mechanism to lean on anyway.
- **Confirmed not dead code**: it's tempting to assume the pgvector column is a half-finished "optional semantic search upgrade" (per the comment on migration 001, line 2) that can be dropped from scope. It is not — `isEmbeddingEnabled()` gates on `OLLAMA_HOST` being set, which it is in this deployment's `.env`, and `searchMemories()` tries the vector RPC *first*, falling back to FTS only on error or empty results (`supabase.ts:84-104`). Any SQLite migration plan that treats sqlite-vec as a "nice to have, do FTS5 first" phase should say so explicitly, because today's default behavior for a normal `memory_search` call is semantic search, not FTS.
